# Paseo GitHub durability boundary

This file governs publication and handoff of work performed through Paseo in this repository. It does **not** define Project Workflow phases, approvals, routing, review verdicts, write scope, or cleanup authority. Recover those from the current default-branch `workflow/ROUTER.md` and the selected workstream's canonical Git records. GitHub Issues and Paseo metadata are not workflow authority.

- Use the legally selected workstream branch/worktree. When creating a workstream, create and publish its corresponding branch on `origin` immediately, then read back that exact remote ref before treating it as available to another context.
- After **every material durable workflow checkpoint**—including implementation, Result, Review, reconciliation, Close, and any state needed for later resumption—commit the exact changes and push them to the corresponding `origin/<branch>`. The coordinator must ensure a delegated contribution is published before consuming it as durable input; neither a local-only worker commit nor a local Task Board update is a handoff.
- After each push, read back GitHub's exact `refs/heads/<branch>` (for example with `git ls-remote --heads origin`) and verify that its SHA equals the expected committed head. Fetch/read back `origin/<branch>` when consuming that branch from another worktree or session. If the ref is absent, stale, divergent, or the push outcome is uncertain, reconcile the exact remote state before retrying; never force-push or proceed on an unverified assumption.
- A local commit, worktree, or file alone is **not durable handoff truth**. Do not advance a dependent Project Workflow obligation, claim remote availability, or hand work to another session/agent until the required commit has been pushed and positively read back from GitHub. If publication/readback is unavailable, report the blocker rather than treating local success as durable completion.
- Do not leave a completed issue/workstream only on a local branch. Retain a published remote branch after branch-scope Close while its Result/evidence may be needed by stabilization integration. Delete it only after safe integration or when canonical Close explicitly authorizes cleanup, with the required exact-head/absence checks.
- Never merge into `main` on your own when the current workflow/program reserves a later joint integration. Publication to the workstream branch is not integration, approval transfer, tracker closure, or permission to change the canonical plan.

For cross-session and cross-agent handoff, **verified GitHub branch state is the durable repository truth**. These publication requirements add no second Task Board, verdict store, workflow gate, or change to Project Workflow semantics.
