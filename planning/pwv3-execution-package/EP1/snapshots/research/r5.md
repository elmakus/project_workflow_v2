## Executive conclusion

The integrated Research supports one coherent architecture.

PWV3 should keep one provider-neutral semantic execution path and add goal as a late-bound execution realization, not as a second workflow. The exact accepted and independently reviewed Execution Package is the common launch artifact for both native_pwv3 and goal. Execution mode is selected only after Execution Package Review. A small late-bound Goal Launch Envelope / Runtime Profile binds the immutable Execution Package to a qualified runtime bundle without changing package semantics.

Goal mode is not valid unless the selected runtime actually supports and uses qualified delegated workers. A main-session continuation loop, even a durable one, is insufficient. PWV3 should own a provider-neutral delegation and completion contract; the provider bundle supplies execution mechanics. For the initial 3.0 contract, delegation depth should be hard-limited to one edge, mutating parallel workers require separate worktrees or stronger isolation, and the goal main/coordinator remains the sole runtime reconciler of worker outputs.

Provider completion is not PWV3 completion. Goal mode may autonomously own implementation, tests, bounded repair, ordinary Review/revalidation, a non-independent Targeted Qualification Campaign, and all other non-independent Final Qualification that can be expressed under the accepted artifact. It then freezes one exact candidate and enters AWAITING_EXTERNAL_GLOBAL_BUG_HUNT. The independent Global Bug Hunt remains outside goal in ChatGPT/OP and is the one normal manual independent-hunt boundary.

After Global, a CLEAR result can continue under a pre-reviewed deterministic disposition policy without a second routine owner CONTINUE prompt. Fresh terminal acceptance remains a distinct PWV3 semantic closure gate, but it can be automatically executed by a qualified read-only, non-authoring, semantically independent reviewer inside the same top-level goal lineage. This does not make a provider terminal bit or provider self-review authoritative: PWV3 still owns the predicate and exact-subject applicability.

An implementation-only Global finding returns to the already-selected execution mode under the same accepted Execution Package plus the exact finding set. Changed implementation produces new immutable Results, repeats invalidated checks/Reviews/targeted qualification, freezes a new qualification epoch, and requires a new applicable independent Global Bug Hunt for the changed exact candidate. Findings that change Execution Package, Plan, Definition, or owner authority route to the earliest semantic owner instead of being silently repaired.

Do not select a goal provider by package name, popularity, or feature count. Define one Goal Launch Envelope, one Goal Execution Report contract, and the PGC-01..32 conformance suite. Qualify exact pinned bundles. The least-machinery strategy is a thin PWV3 provider-neutral adapter over an external goal + subagent + workspace bundle that passes conformance. Fork only when a critical invariant cannot be imposed or verified through the adapter; build a PWV3-native goal engine only if no external bundle can qualify.

All compatible-evolution machinery that can truthfully exist at 3.0 should ship in 3.0. Only performance-oriented material-fingerprint optimization remains genuinely future-only; future-specific readers/converters remain future instances of frameworks shipped in 3.0, not deliberately deferred foundational capabilities.

## 2. Conflict reconciliation: authority, reproducibility, causal fit

The synthesis uses authority and causal fit, not vote counting.

### Launch boundary conflict

W00/R00 treated post-Execution-Package Review as preferred; L06 left the exact lifecycle point open; L18 deliberately left it to integration. L04, L05 and L17 directly tested the boundary against the frozen consumer semantics and provide the strongest causal evidence.

Resolution: **launch after accepted Execution Package Review**.

Reason: under the frozen workflow, Planning may still contain logical work slots. Execution Prep materializes stable Card identity, bounded scope, dependencies, observable acceptance, tests/readbacks and Review obligations. Those are semantic facts, not mere runtime scheduling. A goal launched directly from Plan would either create semantic execution facts in provider-local state or reproduce canonical Execution Prep + Package Review inside the runtime, which semantically collapses back to the post-package boundary with more recovery complexity.

### Plan versus Execution Package

Resolution: the Plan remains provider-neutral and shared, but the **accepted reviewed Execution Package is the common direct launch artifact**. This is the latest safe decision point and gives byte-identical semantic input to both modes.

### Provider completion versus PWV3 acceptance

L01/L07/L18 show that provider completion bits are self-declared or lifecycle-level. Pi agent_end and Paseo completion are not acceptance or even necessarily true quiescence. W00/R00 require PWV3 to own terminal meaning. L16 shows that a semantically independent delegated closure reviewer can execute the PWV3 terminal predicate without a manual stop.

Resolution: provider completion is an input only. PWV3 owns candidate readiness and terminal acceptance. Goal may automate the terminal-acceptance execution through a qualified independent read-only non-authoring delegate, but may not replace the PWV3 predicate with provider status or self-review.

### Targeted Bug Hunt placement

The historical Definition made Targeted and Global external OP boundaries. L10/L16 directly test the R5 operator objective and the quality role of both.

Resolution: replace the universal external Targeted Bug Hunt with a **mandatory non-independent Targeted Qualification Campaign** inside normal execution/Final Qualification. It uses the same reviewed risk/acceptance surface and qualified delegated adversarial workers. A separate external targeted specialty review remains triggerable only when an exact reviewed risk requires independence that neither the internal campaign nor Global can supply.

### Global result and post-result human gate

L10 preserved the historical owner CONTINUE behavior when describing current semantics; L16 demonstrates that the owner-fixed R5 experience cannot be achieved if every clear Global result forces a second routine owner gate.

Resolution: R5 should define a **pre-reviewed deterministic Global disposition policy**. The user manually launches the exact Global attempt. CLEAR continues automatically to fresh terminal acceptance. REPAIR_REQUIRED routes bounded implementation-only defects back to the selected engine. Upstream semantic findings route to their owner. BLOCKED/UNKNOWN fails closed. A human stop remains only for genuine owner authority/discretion, not routine continuation.

### Whether post-Global changed code requires Global again

L18 correctly requires the provider not to decide this by itself. L10/L16/W00 establish exact-subject applicability.

Resolution: the external PWV3/OP contract decides. For any candidate or materially relevant acceptance-surface change, prior Global evidence is not applicable and a new independent Global result is required. Evidence-only repair with no candidate/surface change may preserve Global only when applicability is positively proven.

### Provider preference conflict

L14 identifies pi-goal-x + Paseo-recognized subagents as the strongest frozen host-integration seam. L18 identifies three concrete qualification candidates and explicitly states no production bundle has passed conformance.

Resolution: **no provider winner is selected by Research**. Use the same PGC suite. First qualification should cover Candidate B and Candidate A, with Candidate C as a strong alternate. Selection is a conformance outcome, not an owner guess or popularity judgment.

## 10. Subagent scoping, isolation, reconciliation, recovery and recursion

Scoping:
- child authority is a strict subset of the accepted parent execution obligation;
- children cannot revise the Plan, Execution Package, acceptance surface or current Card;
- workers cannot mark PWV3 semantic completion.

Isolation:
- read-only discovery may share a read-only snapshot if shell/tools are genuinely read-only;
- writable parallel workers require separate worktrees/branches or stronger isolation;
- worktree is file isolation, not OS/network/port/DB/credential isolation;
- runtime resources must be separately allocated or serialized;
- canonical realpath containment and stale-parent-path adversarial tests are required.

Reconciliation:
- goal main/coordinator is the single runtime reconciliation owner;
- it validates scope/currentness, incorporates or rejects child output, resolves conflicts, reruns checks on the composed candidate and records provenance;
- child completion never makes a child branch canonical by itself.

Recovery:
- every dispatch has a stable idempotent ID and run generation;
- ambiguous did-it-run or did-the-effect-happen states are recovered by readback or become RECOVERY_REQUIRED / AMBIGUOUS;
- delayed output from obsolete generations is rejected;
- child commit before parent consumption and parent reconciliation before acknowledgement are explicit crash tests.

Recursion:
- initial 3.0 max delegation depth is one edge;
- remove spawn/delegate tools from workers; prompt-only anti-recursion is insufficient;
- concurrency is finite and belongs in the late runtime profile.

## 11. Mapping internal autonomous loops to PWV3 Result/Review

Do not map provider turns, subagent tasks, internal runtime task boards, test retries, edit loops, session branches, worktree checkpoints or provider-specific goal tasks one-to-one into PWV3 Cards/Results.

Use a semantic envelope around the current stable Card:

1. one current Card remains the PWV3 execution-stage owner;
2. runtime may use zero/one/many internal workers and iterations;
3. intermediate worker/session artifacts are evidence/recovery machinery;
4. when the Card implementation is ready, freeze one exact immutable implementation subject and publish one PWV3 Result;
5. any implementation change after a Result creates a new immutable Result for the same Card;
6. Review/revalidation binds the exact current Result and acceptance surface;
7. implementation-only defects reopen the same Card for bounded repair;
8. semantic findings route upstream;
9. package-level goal execution may cross multiple sequential Cards, but it crosses their normal per-Card semantic cut points and never becomes one monolithic package Result.

This preserves parity between native and goal execution and prevents provider topology from leaking into workflow authority.

## 14. Post-Global defects, bounded repair and reuse of artifact/runtime

Global result handling:

| Result/event | Action |
|---|---|
| CLEAR and exact candidate/surface unchanged | continue to fresh terminal acceptance; no second Global |
| implementation-only repairable finding | return to the same selected execution engine under the same accepted Execution Package + exact finding set; create new Result; repeat invalidated checks/Review/Targeted; freeze new epoch; run Global again for changed candidate |
| qualification evidence defect with no candidate/surface change | repair evidence/process and rerun invalidated qualification; preserve Global only with positive applicability proof |
| Execution Package meaning defect | route to Execution Prep, review new package, start new execution epoch |
| Plan meaning/strategy/dependency defect | route to Planning and re-review |
| Definition/product/owner-authority defect | route to Definition/Brainstorming or explicit owner decision as applicable |
| BLOCKED/UNKNOWN | fail closed and reconcile; no blind retry |
| post-Global integration target movement | evaluate exact delta; material/UNKNOWN impact invalidates affected qualification, including Global where applicability is lost |

The same top-level goal lineage may remain for observability after an upstream change, but the old artifact revision cannot remain current. Close the old epoch, bind the new accepted authority, create a new epoch and re-derive downstream obligations.

## 15. Targeted Bug Hunt and terminal acceptance placement

Targeted:
- replace the universal external OP Targeted Bug Hunt with a mandatory non-independent Targeted Qualification Campaign inside normal execution/qualification;
- require risk hypotheses/critical invariants/held-out checks in the common reviewed artifact;
- use qualified delegated adversarial workers;
- repair bounded implementation defects and repeat the invalidated campaign;
- allow an external specialized targeted review only when a specific reviewed trigger requires independence beyond the internal campaign and Global.

Terminal acceptance:
- remains after an applicable advance-permitting Global result and any returned revalidation;
- is an exact-subject applicability/freshness closure audit, not another broad bug hunt;
- may be automatically dispatched to a qualified read-only non-authoring semantically independent reviewer;
- same top-level goal lineage does not imply same author and does not defeat independence;
- a fresh process alone is insufficient: material authorship/repair relationship and effective write isolation determine independence;
- WAIVED_ACCEPTANCE remains an explicit exceptional owner path, not the normal zero-choreography path.

For the normal R5 operator experience, the user manually invokes Global; a second routine CONTINUE gate after CLEAR is removed in favor of the pre-reviewed deterministic disposition policy.

## 16. Crash/restart, Paseo/worktree currentness and external-effect safety

Canonical recovery order:

1. reconstruct current PWV3 semantic state and exact current obligation from durable repository authority;
2. inspect exact Result/Review/effect state;
3. reconcile Git branches/worktrees/commits;
4. only then attach provider/Pi/Paseo session/agent/task state as runtime evidence;
5. continue only when currentness is proven.

Session persistence is useful but not authority. Never recover by continue latest.

Continuation must be fenced by Pi true settlement, preferably agent_settled or a proven equivalent. An agent_end-only continuation path must fail qualification unless equivalent no-automatic-work fencing is demonstrated.

Paseo:
- use as runtime identity/session/workspace/child-lifecycle substrate;
- child parentage/workspace must be read back after creation;
- non-destructive messages require qualified steer/queue semantics; interrupt is explicit;
- slash-command paths need separate tests;
- ambiguous cancellation fails closed;
- daemon restart must be supervised out-of-band;
- large transcripts are not the sole evidence store;
- exact Paseo × Pi × provider bundle is the qualification unit.

External effects:
- prompt wording is not an enforcement boundary;
- Pi extensions inherit OS authority unless separately constrained;
- provider permission settings do not replace OS/network/credential isolation;
- goal and children receive least authority;
- remote publication is allowed only through a narrow pre-authorized idempotent effect gateway with exact target and readback;
- merge/release/deploy/package publication/destructive host actions remain outside autonomous goal authority unless separately and explicitly added to the accepted policy;
- durable intent -> attempt -> authoritative readback -> verified outcome remains mandatory;
- UNKNOWN occurrence forbids blind retry.

## 17. Adopt provider, interchangeable contract, wrap/fork/build strategy

Recommended hierarchy:

1. **Define interchangeable provider-neutral contract and PGC suite.**
2. **Use a thin PWV3 adapter over a pinned qualified external bundle** when possible.
3. Prefer the exact passing bundle requiring the least provider-specific semantic glue.
4. **Fork only** when a critical invariant cannot be enforced or observed through the adapter, such as true settled continuation, hard effect boundary, worktree isolation or transcript ordering.
5. **Build a PWV3-native goal controller/runtime only** if no external bundle can pass the critical suite through a bounded adapter.

Direct unwrapped third-party goal dependency is insufficient because it leaks lifecycle/schema into PWV3 and cannot guarantee the common stop/effect/result contract. A provider bundle with no PWV3 adapter is acceptable only if it natively exposes the whole provider-neutral contract; none has been proven to do so.

Initial qualification order:
- Candidate B: current tmonk/pi-goal-x + a Paseo-supported qualified subagent/worktree bundle;
- Candidate A: frozen pi-mono-goal + team-mode after the identified lifecycle/Paseo/tool-boundary gaps are addressed;
- Candidate C: current @narumitw/pi-goal + qualified subagent/worktree bundle as a strong alternate.

This is a test order, not a selected winner.

## 20. Version and compatibility semantics after consolidation

Preserve semantic version meaning:

- 3.0.x = contract-preserving maintenance/bug-fix evolution;
- a new compatible durable contract generation = 3.1+;
- a change that cannot safely interpret/preserve valid prior lineage = major boundary.

Ship in 3.0.0:
- explicit contract-version envelope per durable artifact;
- artifact-kind-specific monotonic contract generation, independent of product semver;
- reader registry and canonical in-memory projection;
- unsupported/unknown-newer fail-closed behavior;
- conversion/migration interfaces that create successor revisions without rewriting immutable evidence;
- compatibility matrix and adoption/downgrade preflight;
- reader lifecycle metadata;
- synthetic old/current/newer/unknown/malformed/breaking fixtures;
- safe roll-forward/adopt transaction;
- proof-based downgrade refusal;
- provider/runtime qualification tuple.

Track compatibility across:
1. exact PWV3 product/package release;
2. durable artifact contract generation by kind;
3. helper/API contract;
4. exact Pi/runtime identity;
5. exact Paseo identity where used;
6. goal provider/adapter;
7. delegated-worker/workspace realization;
8. provider/model capability class and execution surface where material;
9. conformance-profile revision/result.

Semver is an intent signal, never compatibility proof.

Roll-forward:
- exact source/target identities;
- quiesce unsafe in-flight work;
- bind artifact contracts and current obligation;
- require target conformance;
- publish adoption intent;
- positive target-side readback;
- re-derive the same legal obligation before continuation.

Downgrade:
- never automatic;
- prove all required artifacts readable, current semantics representable, pending attempts/effects interpretable and goal/subagent tuple qualified;
- UNKNOWN -> refuse.

Long-run qualification must cover compaction, restart/reopen, large histories, active/finished subagents and repeated resume cycles. Provider selection remains separate from popularity.
