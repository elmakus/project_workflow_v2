## 3. Bounded Technical Design

These are P1 representation/implementation choices within D12, subject to independent Plan Review. They do not select a runtime/provider or mandate external product architecture.

### 3.1 One core, explicit ports

Use a plain Node ESM helper with a qualified Node LTS baseline (minimum Node 22 API surface), versioned JSON machine artifacts and UTF-8 Markdown human authority/coverage documents. Freeze encoding/path/number rules and golden vectors in S01; reject duplicate keys, ambiguous encodings and unsupported values before canonical use. Runtime baseline support is verified per exact package, not inferred from the version label.

Keep four separable responsibilities:

1. **Contracts and pure decisions:** verified-input validation, relational closure, owner classification, derive-next, applicability/affected cone and diagnostic projections. One implementation of semantic policy.
2. **Verified observation and effects:** Git object resolution, remote freshness, current capability/health observations, fenced publication and effect readback. Unverified caller booleans are not evidence.
3. **Stateless helper operations:** inspect/resume/derive-next, validate, context-pack, health/doctor/handshake, publish/readback, effect reconciliation, evolution proof/transition. Operation names may be refined without changing acceptance.
4. **Thin host surfaces:** ChatGPT bootstrap/action realization and globally delivered Pi/Paseo bindings plus CLI/debug over the same helper. No mandatory MCP, host semantic plugin, custom scheduler or second routing table.

The installed helper has no workflow DB, hidden semantic cache, agent registry or session journal. Temporary object caches must verify identity and may be deleted without losing truth.

### 3.5 OP caller contract and owner gates

### 5.2 Qualification candidate and fresh terminal semantics

Q0 is a runnable candidate, not GA. Qualification may reveal repairs. Every change records affected-cone classification and reruns invalidated checks/Reviews/host evidence. Candidate/surface change requires a new applicable Global; a prior hunt is not transferred by name. Before terminal acceptance, fix corrected **QF** and the current acceptance manifest, prove applicability of all required prior qualification, then establish the single current terminal-attempt frontier and produce a **new** result. Historical acceptance later shown applicable cannot satisfy freshness.

A new same-binding terminal attempt first durably supersedes the old one. Current RED/BLOCKED/UNKNOWN/stale/ambiguous evidence blocks even if an older success exists. Only the newest applicable frontier is reconstructible as current. A qualified read-only, non-authoring semantically independent closure reviewer may run automatically after CLEAR; a self-reviewing executor cannot. An owner waiver must name exact QF and current acceptance and be durably published/read back; no preselected blanket waiver is part of this plan.

Global repeat before integration intent supersedes even a completed terminal success and blocks integration until the successor Global plus fresh terminal acceptance complete. Intent-cut uncertainty itself blocks repeat/integration replay until authoritative reconstruction resolves it. Cover cuts on both sides, not just happy-path labels.

Product payload identity and integration/acceptance evidence identity are distinct exact subjects. The package manifest enumerates which bytes affect executable/semantic product behavior. Adding evidence may preserve QF only after proven non-impact; final candidate checks still cover the actual integrated context. This avoids impossible hash self-reference without weakening candidate/surface freshness.
